How I Got Into Data

My interest in data engineering grew as I became more involved in solving technical problems and understanding how data moves through systems. The more I worked with data, the more I realized that reliable systems and trustworthy information have a direct impact on business decisions.

What keeps me interested is that data engineering sits at the intersection of three things I care about: engineering rigor, business context, and continuous learning. Every pipeline is a puzzle—understanding the source, designing the transformation, ensuring quality, and making it reliable.

I particularly enjoy governance work because it's about building trust. When you have proper data quality checks, clear lineage, and good documentation, stakeholders stop questioning the numbers and start using them to make decisions. That's satisfying.

Right now I'm exploring RAG systems and AI platforms because I believe the next generation of data engineering will involve making data not just reliable, but AI-ready. But my core focus remains the same: building systems that people can trust.

Experience

What I've Learned at Accenture

Data Engineer · Accenture

Feb 2024 – Present · Bengaluru, India

A

When I joined Accenture, I worked with existing data pipelines that were functional but difficult to maintain and troubleshoot. My focus shifted from just "making it work" to understanding why it was hard to debug.

I focused on three things: configuration-driven design, comprehensive testing, and clear process logging.

Instead of hardcoding values in scripts, I built a JSON-based configuration framework. This meant new pipelines could be created by modifying a config file instead of writing new code. It made deployments faster and made onboarding new team members much easier.

I also learned that testing isn't optional—it's essential. I wrote tests for everything, achieving high coverage across pytest suites. This caught bugs before they hit production and gave me confidence to make changes without breaking things.

The third area was observability. When a pipeline fails, you need to know why without digging through logs for hours. I implemented process logging tables that track batch IDs, execution times, and error details. This made troubleshooting faster and helped identify patterns in failures.

Beyond the technical work, I've learned that data engineering is fundamentally about communication. Understanding what business users actually need, explaining tradeoffs to stakeholders, and documenting decisions so others can understand them later.

I actively study and learn from open-source projects such as urllib3, Axios, and Dagster. This exposes me to different codebases and engineering standards, which helps me improve my own work.

Projects

Projects & What I Learned

Kafka → PySpark → Delta Pipeline

Why I built it: I wanted to understand exactly-once semantics in streaming. Most tutorials show how to build a pipeline, but they don't explain what happens when things fail.

What problem it solved: Streaming data is messy—duplicates, late arrivals, schema changes. I implemented checkpointing, idempotent writes, and schema validation to handle these edge cases.

What I learned: Exactly-once semantics are worth the complexity. They require understanding the entire data flow—from Kafka offsets to Delta Lake transaction logs. Testing streaming systems is different from batch systems.

Cloud Data Platform

Why I built it: Infrastructure as Code is essential for reproducible deployments. I wanted to create a template that could be used across environments without manual configuration.

What problem it solved: Manual infrastructure setup is error-prone and hard to reproduce. I used Terraform to define Azure Event Hubs, Databricks, and ADLS resources.

What I learned: Terraform modules are powerful but require careful design. I learned to think about state management, resource dependencies, and rollback strategies. Infrastructure code needs the same level of testing as application code.

RAG Document QA Chatbot

Why I built it: I wanted to understand how vector databases and LLMs work together. This was an experiment to learn, not a production system.

What problem it solved: Building a chatbot that can answer questions about documents requires more than just an LLM. I implemented vector search with ChromaDB, response caching to reduce API calls, and modular interfaces.

What I learned: RAG systems are more complex than they appear. Retrieval accuracy depends heavily on chunking strategy and embedding quality. Caching is essential for cost control when using paid APIs.

How I Work

My Approach

Curiosity

I don't accept "that's how it's done" as an answer. I ask why. I read documentation. I look at source code. I want to understand the tradeoffs in every decision. This sometimes slows me down initially, but it leads to better long-term solutions.

Ownership

When I take on a task, I see it through. This means testing thoroughly, documenting clearly, and monitoring after deployment. If something breaks, I investigate and fix it. I don't hand off half-finished work.

Continuous Learning

Technology changes quickly. I spend time learning new tools—not just the syntax, but the philosophy behind them. I actively study open-source projects like urllib3, Axios, and Dagster to understand how production-grade software is built.

Attention to Detail

Data engineering requires precision. A small schema change can break downstream systems. A missed edge case can cause data corruption. I'm meticulous about testing, validation, and documentation. This has prevented production issues more times than I can count.

Collaboration

Data engineering doesn't happen in isolation. I work closely with data analysts, business stakeholders, and other engineers. I make an effort to understand their needs, explain technical tradeoffs in plain language, and document decisions so others can understand them later.

Analytical Thinking

When a pipeline fails or data doesn't match expectations, I don't guess. I investigate. I look at logs, query the data, check the configuration, and trace the execution path. Root cause analysis is a skill I've developed through experience.
